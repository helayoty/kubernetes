# CLAUDE.MD - AI Assistant Guide for Kubernetes

This file provides context and guidance for AI assistants (like Claude) working with the Kubernetes codebase.

## Project Overview

Kubernetes (K8s) is an open-source system for automating deployment, scaling, and management of containerized applications. This is the main Kubernetes repository containing the core system components.

- **Language**: Primarily Go
- **License**: Apache 2.0
- **Community**: Part of the Cloud Native Computing Foundation (CNCF)
- **Documentation**: https://kubernetes.io

## Repository Structure

### Key Directories

- **`cmd/`** - Command-line tools and binaries (kubelet, kube-apiserver, kubectl, etc.)
- **`pkg/`** - Core Kubernetes packages and libraries
- **`api/`** - API definitions and OpenAPI specs
- **`staging/`** - Staged Go modules published separately (client-go, api, etc.)
- **`test/`** - Test suites including e2e, integration, and unit tests
- **`hack/`** - Scripts for development, building, and testing
- **`build/`** - Build configuration and Docker images
- **`cluster/`** - Cluster deployment and setup scripts
- **`vendor/`** - Vendored dependencies
- **`third_party/`** - Third-party code and tools
- **`plugin/`** - Admission and scheduler plugins
- **`docs/`** - Design docs and proposals

### Important Files

- **`Makefile`** (symlink to `build/root/Makefile`) - Build system entry point
- **`go.mod`** / **`go.work`** - Go module definitions
- **`OWNERS`** / **`OWNERS_ALIASES`** - Code ownership and review assignments
- **`.go-version`** - Required Go version
- **`CONTRIBUTING.md`** - Contribution guidelines

## Development Workflow

### Building

```bash
# Build all binaries
make

# Build specific component
make WHAT=cmd/kubelet

# Quick build (skips tests and validation)
make quick-release
```

### Testing

```bash
# Run unit tests
make test

# Run unit tests for specific package
make test WHAT=./pkg/kubelet/...

# Run integration tests
make test-integration

# Run e2e tests
make test-e2e
```

### Code Quality

```bash
# Run verification (lint, format, generated files)
make verify

# Update generated code and vendor
make update

# Run specific verification
./hack/verify-*.sh
```

## Important Conventions

### Code Organization

1. **Staged repositories**: Code in `staging/src/k8s.io/*` is published as separate modules
2. **API versioning**: APIs follow strict versioning (alpha, beta, stable)
3. **Generated code**: Many files are auto-generated (boilerplate, deepcopy, clients, etc.)

### File Patterns

- `*_generated.go` - Auto-generated, do not edit manually
- `zz_generated.*.go` - Auto-generated by code generators
- `doc.go` - Package documentation
- `types.go` - API type definitions
- `*_test.go` - Test files

### Common Commands

```bash
# Verify everything before submitting
make verify

# Update generated code after API changes
make update

# Build and test specific component
make WHAT=cmd/kube-apiserver && make test WHAT=./pkg/apiserver/...

# Run gofmt
./hack/update-gofmt.sh

# Verify dependencies
./hack/verify-vendor.sh
```

## Working with This Codebase

### Before Making Changes

1. **Read existing code** - Always read files before modifying
2. **Check OWNERS** - Identify relevant code owners
3. **Run tests** - Verify current state before changes
4. **Check generated files** - Don't manually edit generated code

### Making Changes

1. **Keep it focused** - Make minimal, targeted changes
2. **Follow conventions** - Match existing code style and patterns
3. **Update tests** - Add/modify tests for changed behavior
4. **Update generated code** - Run `make update` after API changes
5. **Verify everything** - Run `make verify` before committing

### Testing Changes

1. **Unit tests** - Fast, focused tests for specific packages
2. **Integration tests** - Test component interactions
3. **E2E tests** - Full system tests (slower, more comprehensive)
4. **Verify scripts** - Automated checks for code quality

## Common Gotchas

1. **Generated code** - Many files are auto-generated; look for `// +k8s:` directives
2. **Staged repos** - Changes in `staging/` may affect multiple published modules
3. **API compatibility** - API changes require careful versioning and deprecation
4. **Vendor dependencies** - Use `go mod` and run `./hack/update-vendor.sh`
5. **Build tags** - Some code uses build tags for different platforms/configurations

## Key Components

### Core Components (cmd/)

- **kube-apiserver** - API server, handles REST requests
- **kube-controller-manager** - Runs control loops
- **kube-scheduler** - Schedules pods to nodes
- **kubelet** - Node agent, runs containers
- **kube-proxy** - Network proxy on each node
- **kubectl** - Command-line client

### Key Packages (pkg/)

- **pkg/api** - Internal API representations
- **pkg/kubelet** - Kubelet implementation
- **pkg/scheduler** - Scheduler logic
- **pkg/controller** - Controller implementations
- **pkg/apiserver** - API server core
- **pkg/registry** - API storage layer

## Tips for AI Assistants

1. **Always read before writing** - Never modify files without reading them first
2. **Respect generated code** - Don't edit files marked as generated
3. **Follow existing patterns** - Match the style and structure of existing code
4. **Be conservative** - Kubernetes has strict compatibility requirements
5. **Test thoroughly** - Run relevant tests before considering changes complete
6. **Check dependencies** - Be aware of staging/ and module boundaries
7. **Use make targets** - Leverage the existing build system rather than direct go commands
